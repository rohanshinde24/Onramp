# Operations

How to see what Onramp is doing, and how I found two real defects with it. The telemetry is
OpenTelemetry end to end: every process role exports traces, metrics and logs to one collector.

## Running it

```sh
make observe        # the application plus the observability container
make observe-down
```

Grafana is at `http://localhost:3300` with the Onramp dashboard, Tempo for traces, Loki for logs
and Prometheus for metrics, all in one `grafana/otel-lgtm` development container. That container
is a convenience for local work, not a production topology. Containers export to it through
`CONTAINER_OTLP_ENDPOINT`, which `make observe` sets. A process on the host exports to it with
`OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4318`. Without an endpoint, spans and metrics are
still created (trace IDs still appear in logs and cross every boundary) but nothing is exported.

`deploy/observability/promq.sh` runs a Prometheus query and `deploy/observability/trace_tree.py`
prints a trace as a tree; the walkthroughs below use both. The dashboard is generated by
`deploy/observability/build_dashboard.py`.

## One trace per fact

Each role reports as its own service, `onramp-<role>`. A trace follows a fact across every
boundary it crosses:

1. The API's request span (FastAPI instrumentation), with a client span per SQL statement
   (operation and database only, never the statement text or parameters).
2. The direct Temporal start or signal from the API (Temporal's tracing interceptor).
3. The outbox. When code emits an event, the W3C trace context of the current span is stored in
   the outbox row's `trace_context` column, in the same transaction as the business change.
4. The publisher opens a `publish <topic>` producer span under that stored context and sends the
   context in Kafka headers. A retry is another publish span in the same trace.
5. Each consumer processes the message in a `process <topic>` consumer span under the publish
   span. The post-commit Temporal signal runs inside it, so the workflow it wakes joins the
   trace.
6. Workflow activities, the checks, the investigation (with a span per model call, tool call and
   policy search) and the Action Gateway (`gateway.execute`, with one `marketplace.write` span
   per attempt) run inside the workflow's trace. Marketplace events emitted by a gateway write
   carry the gateway's context into their own outbox, so they continue the same trace.

Case transitions are span events on whatever span staged them.

Tool spans record the tool name and how many references it returned, never the arguments: a
search query can echo worker-supplied text.

## Logs

Logs are JSON on stdout and, with an endpoint, the same records go to Loki. Every record carries
the correlation fields bound for its unit of work (`request_id`, `tenant_id`, `case_id`,
`workflow_id`, `event_id`, `correlation_id`, `causation_id`) and the active `trace_id` and
`span_id`. Everything logged about one case, across roles:

```
{service_namespace="onramp"} | case_id="case_..."
```

A request ID sent in `X-Request-ID` is echoed in the response and attached to that request's
logs, which gives the trace ID.

| `onramp.model.call.duration` | histogram (s) | model, result | Latency of one model request |
| `onramp.agent.tool_calls` | counter | tool, result | Investigator tool calls |

| `onramp.consumer.messages`, `.duration` | counter, histogram (s) | group, event_type, outcome | Consumed messages: applied, duplicate, ignored, parked |

| `http_server_*` | FastAPI instrumentation | http_target, http_status_code | API requests |

Business counters are recorded only when the transaction that staged them commits; a rolled-back
savepoint drops only what it staged. A gauge whose value cannot be read stops reporting instead
of repeating its last value. In Prometheus, dots become underscores and counters gain `_total`.

## Walkthrough: events stop reaching consumers

**Symptom.** Cases resolve normally in the console, but nothing downstream sees their events:
the dashboard's outbox backlog climbs and its oldest unpublished event keeps getting older.

I reproduced this by stopping the Kafka broker at 18:18:27 and having a Globex operator accept
two payout proposals and a lead approve the one that needed an adjustment.

**1. Is work still happening?** Both cases reached `resolved`. The API signals Temporal directly
as well as through events, so the outage did not stop case progress. That narrows the problem
to event delivery.

**2. What is stuck?** About 25 seconds in:

```
$ deploy/observability/promq.sh 'onramp_outbox_backlog'
{'source': 'marketplace'} 2
{'source': 'onramp'} 6
$ deploy/observability/promq.sh 'onramp_outbox_oldest_age_seconds'
{'source': 'marketplace'} 20.9
{'source': 'onramp'} 23.4
$ deploy/observability/promq.sh 'sum by (topic) (increase(onramp_outbox_publish_failures_total[10m]))'
{'topic': 'onramp.actions'} 6.6
{'topic': 'marketplace.payments'} 4.6
```

Both producing databases have unpublished events, and sends are failing for several topics at
once, so the cause is shared: the broker or the path to it, not one event.

**3. Which request, and what happened to its event?** Loki gives every log line for the case
with its trace ID:

```
{service_namespace="onramp"} | case_id="case_ba4ad6025a814cdd89834ec2e7dd4e6b"
onramp-api       outage-accept-...   bd98cff69a9f  case transition staged proposed -> awaiting_approval
onramp-api       outage-approve-...  cc07a8d92a95  case transition staged awaiting_approval -> executing
onramp-workflow-worker               d98d1d050637  case transition staged executing -> verifying
onramp-workflow-worker               d98d1d050637  case transition staged verifying -> resolved
```

The trace of the operator's accept request:

```
$ python3 deploy/observability/trace_tree.py bd98cff69a9f937141c076ded774ae42
POST /proposals/{proposal_id}/accept  [onramp-api] 70.0ms
  StartWorkflow:CaseWorkflow  [onramp-api] 34.2ms
  SignalWorkflow:case_changed  [onramp-api] 15.4ms
  publish onramp.actions  [onramp-outbox-publisher] 15229.7ms  ERROR: KafkaError{code=_MSG_TIMED_OUT,...}
  publish onramp.actions  [onramp-outbox-publisher] 15429.3ms  ERROR: KafkaError{code=_MSG_TIMED_OUT,...}
  publish onramp.actions  [onramp-outbox-publisher] 15508.2ms  ERROR: KafkaError{code=_MSG_TIMED_OUT,...}
  publish onramp.actions  [onramp-outbox-publisher] 15485.3ms  ERROR: KafkaError{code=_MSG_TIMED_OUT,...}
  publish onramp.actions  [onramp-outbox-publisher] 3475.7ms
```

The request committed and signalled the workflow; its `proposal.accepted` event then failed to
publish four times, each after the 15 second delivery timeout, and the publisher's logs say
`Failed to resolve 'kafka:19092'`. **Root cause: the broker is down.** The trace also shows that
nothing was lost: the event stayed in the outbox and the fifth attempt, after the broker came
back at 18:19:31, succeeded. The backlog was empty at 18:19:47.

**4. Did the consumers catch up?** This is where the telemetry was wrong. Kafka's own view
showed `onramp-case-signals` six messages behind and `onramp-case-evidence` two behind for about
50 seconds after the broker returned, while each consumer rejoined its group after its 45 second
session timeout. The `onramp.consumer.lag` gauge said zero the whole time, for two reasons:

* Lag was summed over the member's assigned partitions, and a member that has lost its session
  has none, so it computed zero. Fixed in `eba23cf`: lag now comes from the group's committed
  offsets over every subscribed partition.
* Even computed correctly, lag can only be read through the group coordinator, which is not
  there during the outage or the rejoin. Repeating the outage after the first fix, the reads
  failed for that minute and the series stopped, and Prometheus kept answering with the last
  value, zero, for its five minute lookback. Fixed in `63f9adf` with
  `onramp.consumer.lag.age`, the seconds since the last successful read, which keeps reporting
  and grows while reads fail. The dashboard shows it beside lag.

Repeating the outage with both fixes (broker stopped 19:03:32, started 19:04:40), the age climbed
from 9.8 to 69.9 seconds while the broker was down and fell back under 2 seconds at 19:05:01,
about 20 seconds after the broker returned. An alert on an age above 60 seconds would have
fired during the outage instead of the dashboard showing a reassuring zero.

## Found while building this: a consumer that could never recover

Bringing the full stack up for the first time with telemetry, the case-signal consumer
restarted in a loop. Its logs showed `WorkflowAlreadyStartedError` from the post-commit hook.
Kafka had been recreated without a volume earlier, so events written to the outbox while it was
gone were published afterwards, including events for a case whose workflow had already
completed. A case workflow completes only when its case is terminal, and the coordinator's reuse
policy refuses to start it again, so the start-then-signal raised. The hook runs before the
offset commit, so the same message was redelivered and failed on every restart, blocking every
event behind it on that partition. Fixed in `d7ec75a` with a workflow test that signals a
finished case: a completed workflow now means there is nothing to wake.

## Running on Kubernetes

The roles also run on a local kind cluster, packaged with Kustomize (ADR-013). Postgres, Kafka,
Elasticsearch, Temporal and the telemetry backends stay under Compose; the kind node joins the
Compose network and pods use the Compose names.

```sh
make k8s-up        # Compose dependencies, stop the Compose roles, kind cluster, KEDA 2.21.0
make k8s-deploy    # build both images, load them, run the setup Job, roll out every role
make k8s-status    # deployments, pods, scaled objects, autoscalers, jobs
make k8s-down      # delete the cluster (the Compose dependencies keep running)
```

The API is at `http://127.0.0.1:8180`. `make k8s-deploy` tags images by ID, so a deploy with no
code change restarts nothing and a change restarts only the roles whose image changed. Before
each rollout the `onramp-setup` Job runs migrations, creates Kafka topics, and loads and indexes
the policy corpus baked into the ml image. The agent worker is off: `ANTHROPIC_API_KEY=...
make k8s-agent` adds it with your key, and then investigations call the model and cost money.

Each role's probes, shutdown budget and scaling signal are in the deployment table in
`docs/ARCHITECTURE.md`. The whole node, with KEDA and the collector, used about 1.7 GiB; the
Onramp pods used 70 to 150 MiB each, which set their memory requests.

### What I checked on the cluster

Commands are from the repository at `d25f677`, on one kind node (Kubernetes 1.37) in Docker
Desktop with 8 GB on a 16 GB laptop.

| Check | Command | Result |
|---|---|---|
| A case end to end | open a payout case through the NodePort, accept its proposal | the cluster's workflow worker ran checks and proposed; the accept resolved it; the cluster's publisher and case-signal consumer delivered the fallback event, ignored as already applied |
| API rollout under traffic, 10 s `preStop` | `make k8s-rollout-check` (three runs) | 0 failed of 9,841 requests |
| The same with a 5 s `preStop` | as above, earlier manifest (three runs) | 2 failed of 7,165, all in one run |
| The same with no `preStop` (control) | as above, sleep patched out (two runs) | 81 failed of 5,175 (`RemoteDisconnected`) |
| Database outage, 45 s | `docker pause onramp-postgres-1` | both API pods NotReady and out of the Service; every other role Ready; no restarts; full recovery |
| Database hung past two minutes | the same pause for 170 s | publisher and relay loops blocked in a query and failed liveness, as designed for a hung call |
| Lag autoscaling | `backend/.venv/bin/python deploy/k8s/kind/lag_burst.py 20000` | event consumer 1 to 3 replicas while the burst was published, back to 1 about two minutes after it drained; 20,000 events processed, 20,000 distinct |
| Backlog autoscaling | `kind-agent` overlay with a placeholder key and a closed local model URL | agent worker 0 to 1 on one queued task, back to 0 once the queue was empty; no model request left the pod |

The 170-second pause found that database connections had no connect timeout or keepalives,
so a lost database blocked calls indefinitely. Connections now time out after 5 seconds and
use TCP keepalives (`af4df41`). A database that accepts connections and never answers is
still caught only by the loop heartbeat, which is what restarts the publisher.

### Limits of these checks

* One node and laptop timings. The `preStop` margin depends on how fast endpoint removal
  propagates; staging needs its own rollout check.
* The lag burst uses events that do nothing, so it shows the scaling decision and exactly-once
  processing across rebalances, not throughput. Throughput is Phase 20.
* The backlog test's queued task was an orphan from an earlier session whose workflow had
  moved on. It showed that a stale backlog estimate keeps the agent worker scaled up until a
  worker polls once and Temporal discards the task.
* Kafka here is a single broker without a volume (Compose), and Temporal is the development
  server. The cluster shows the roles, not those dependencies.

## Limits

* One development container holds the backends, with no persistence; it restarts empty. On
  Kubernetes a collector in the cluster sits in front of it; managed backends are staging work.
* Every span is sampled and every SQL statement is a span. Fine locally; a deployment needs a
  sampling decision.
* No alert rules are defined yet. The dashboard shows the signals an alert would use (backlog
  age, consumer lag, gateway failures, activity failures).
* After a role restarts, Prometheus keeps its previous series for five minutes. Panels for
  single-writer gauges use `max` so the old series cannot inflate a total.
* The API's direct Temporal start or signal and the later Kafka-driven signal appear in
  different traces when the workflow was started before the request; the case ID in logs links
  them.
